# ADR-0005：稽查助手改為即時對答，法規放進 Bedrock 知識庫

| | |
|---|---|
| 日期 | 2026-09-13 |
| 狀態 | 已採納 |
| 影響 | `SPEC.md` §7.2、§8.10（新增）、§10.2；`infra/template.yaml`；`backend/chat.py`；`frontend/src/components/ChatWidget.tsx` |
| 推翻 | SPEC §10.2「Bedrock ≤ 1 RPS → 所有 LLM 產出離線批次預算」 |

## 問題

稽查人員要的是出發前直接打一句「○○幼兒園最近狀況如何」，拿到兩件事：
這間園的風險現況，以及依它過去的違規類型、這次該查哪些法規。

派工單（§8.9）已經給了前者的固定版本，但回答不了臨時的問題，也沒有法規原文。
原本的決議是「Bedrock 每秒 1 次，所以不做即時 LLM」——這把**限流**當成**禁止**。
規範要求的是速率，不是時機。

## 決定

### 一、即時對答，但每一個 Bedrock 請求都在節流器裡

| 環節 | Bedrock 請求數 | 保證方式 |
|---|---|---|
| 一題問答 | 恰好 2（知識庫 Retrieve、Claude 生成） | `BedrockPacer` 讓兩者間隔 ≥1.1 秒，回應前再補足間隔 |
| 同時兩題 | 0（第二題被拒） | `ChatFunction` reserved concurrency = 1，Lambda 直接回 429 |
| 被限流或失敗 | 不重試 | SDK 重試全關；退回 §8.8 模板摘要，`source = fallback` |
| 園名多筆相符、訊息含人名 | 0 | 在呼叫 Bedrock 前就回應 |

「回應前補足間隔」是必要的：reserved concurrency 只保證不重疊，
下一題可能落在另一個容器、緊貼著上一題的最後一個請求。
讓函式多等到 1.1 秒才結束，佔住那唯一的並行名額，跨容器也成立。

### 二、知識庫用 Bedrock Knowledge Bases + S3 Vectors，但不用批次匯入

`StartIngestionJob` 由 Bedrock 自己決定嵌入的速度，我們管不到，
一次灌 600 份等於在短時間內打出數百個嵌入請求。

改成：

1. `etl/laws.py` 先把 PDF 切成**一條條文一份文件**（chunking = NONE），
   一份文件恰好對應一次嵌入
2. `infra/rag/setup_kb.py` 用 custom data source 的 `IngestKnowledgeBaseDocuments`
   **一次送一份**，輪詢到 `INDEXED` 才送下一份，所有 Bedrock 呼叫（含輪詢）走同一個節流器

代價是匯入要約 50 分鐘，而且匯入期間不能 Demo 助手。

為了不讓知識庫卡住整個功能，助手有**基礎模式**：只設 `CHAT_ENABLED`、不設 `KB_ID` 時，
跳過檢索（一題只剩 1 個 Bedrock 請求），用園況資料回答，prompt 禁止引用任何法條，
回應帶 `laws_enabled: false`，前端顯示「未附法規依據」。

S3 Vectors 而非 OpenSearch Serverless：後者有最低 OCU 費用，且本案只有數百份文件。

### 三、語料只收核心 24 部，另補新北裁罰基準附表

`法規/` 有 155 份 PDF。先收稽查現場會引用、或新北裁罰實際涉及的 24 部（清單與理由在
`etl/laws.py` 的 `CORE`），切出 592 份文件。師資培育、教師證書、各類補助與獎勵要點
不收——與稽查無關，只會稀釋檢索。

`新北市政府處理違反幼兒教育及照顧法與教保服務人員條例事件裁罰基準` 本文只有兩點、
寫著「如附表一、附表二」，而收錄清單沒抓到附表。附表才是「違反哪條 → 罰多少」的
對照，對稽查最有用，另從新北市法規查詢系統下載，依表格列切成 18 份。

### 四、模型用 Claude Opus 4.6

2026-09-13 在競賽帳號實測：Opus 5、Sonnet 5、Opus 4.8、Opus 4.7 皆回 403
（not available for this account）；Opus 4.6、Sonnet 4.6、Haiku 4.5 可用。
取可用者中能力最高的 Opus 4.6，`effort: low`。實測含園況與 6 則條文的問題，第一版 prompt 輸出 758 tokens、生成 14.2 秒，超過逾時預算而退回模板；改為限 350 字、`max_tokens` 1,200、不用 Markdown 後，三題實測整題 4.9–9.7 秒。
依規範第 2 條，只使用這一個生成模型與 Titan Text Embeddings V2。

## 三道防線

1. **LLM 不碰分數**：分級、名次、裁罰紀錄從 `ServingStore` 取出原樣放進 prompt；
   前端顯示的園所卡片也直接取自 store，不經 LLM。
2. **引用可回溯**：prompt 限定只能引用檢索到的條文；後端再比對一次，
   回答中出現、但不在檢索結果裡的法規或條號放進 `unverified_refs`，前端顯示警示。
3. **個資不送出**：訊息含「負責人：某某」或「姓氏＋老師／園長…」樣式時直接擋下，
   不送 Bedrock、log 也不記問題原文。這是樣式比對不是姓名辨識，前端另有提示。

## 盤點時發現的資料問題

裁罰紀錄的 `law` 欄位**沒有標明是哪一部法規**。例如 `第33條第1項教保服務人員對幼兒有
非屬情節重大之不當對待行為` 是《教保服務人員條例》第33條，而《幼兒教育及照顧法》
第33條是緊急傷病處理。`etl/categories.py` 以述文關鍵字優先分類，類別本身不受影響；
但**不能把紀錄上的條號直接當成幼照法條號**去對知識庫。

因此：知識庫文件不附「類別」metadata（原本想用 `ARTICLE_RULES` 對幼照法條號標類別，
會標錯）；檢索改用裁罰**類別**轉成的關鍵字，prompt 也明確告知條號可能屬於另一部法規、
且可能是 2023 年修法前的舊條號。

## 沒有採納的選項

- **維持離線、每園預先生成一段建議**：回答不了臨時問題，也等於把 1,178 份文字塞進 serving
- **自己算向量、不用 Knowledge Bases**：速率一樣可控，但使用者指定要用 Knowledge Bases
- **StartIngestionJob 批次匯入**：快，但嵌入速率不在我們手上，無法證明守住每秒 1 次
